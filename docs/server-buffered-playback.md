# Серверный буфер A/V — 0.3.9 и новее

В выпуск **0.3.10** включена ревизия `1.13.11-ts3stream.4`: исправления кеша и упорядочивания ниже, плюс диагностические счётчики пересылки. По поведению она эквивалентна ранее установленной `1.13.11-ts3stream.3-diagnostic`. Плагин 0.3.10 добавляет клиентский выбор битрейта с начальным значением 4000 Кбит/с; это не дополнительный клиентский буфер. [Описание выпуска](release-0.3.10.md). Оставшиеся WAN-зависания не объявляются устранёнными.

В режиме **server** двухсекундный буфер находится в доработанном LiveKit. Плагин не добавляет 2 секунды к PCM и не запрашивает двухсекундный клиентский видеобуфер. Небольшие буферы WebRTC и аудиоустройства остаются.

## Почему заменён режим 0.3.8

Длинный тест выявил конфликт фиксированной компенсации PCM с внутренней синхронизацией WebRTC: после двух минут медиана видео была 2027,5 мс, аудио — 2396,8 мс. Внутренняя цель аудиобуфера росла, появлялись вставленные для замедления сэмплы. Короткие тесты 0.3.8 не обнаруживали этот эффект и не доказывали длительную синхронизацию.

Серверный прототип после трёх минут: видео **2072,1 мс**, звук **2073,1 мс**, разница **0,9 мс** на выходных колбэках. Это локальное измерение, не гарантия для любых устройств/сетей. Полная матрица проверок приводится в заметках релиза.

## Установка

Новые Linux/Windows-установки выбирают серверный режим и скачивают **TS3Stream LiveKit** из того же релиза:

```ini
TS3STREAM_BUFFER_MODE=server
TS3STREAM_PLAYOUT_DELAY_MS=2000
# Если SFU не на localhost:7880, задать его внутренний HTTP(S)-адрес:
TS3STREAM_LIVEKIT_INTERNAL_URL=http://127.0.0.1:7880
```

Сам бинарник control API без `TS3STREAM_BUFFER_MODE` сохраняет legacy-режим для существующих конфигураций. При повторной установке прежние режим/задержка сохраняются. Явное переключение: Linux `--buffer-mode server --playout-delay-ms 2000`, Windows `-BufferMode server -PlayoutDelayMs 2000`. `0` отключает добавленную задержку.

Control API проверяет `/ts3stream/buffering` перед выдачей токена серверного режима. Со стандартным LiveKit выдача такого токена вернёт 503, а не молча создаст комнату без буфера. Маркер `ts3stream-server-av-v1:2000` подписывается в конфигурации новой комнаты; min/max клиентского playout delay равны нулю, `syncStreams=true`.

## Обновление действующего сервера

1. Сохранить старые бинарники LiveKit/control API и конфиги.
2. Установить `ts3stream-livekit-linux-amd64` как `/opt/ts3stream/bin/livekit-server` (Windows: `ts3stream-livekit.exe` как `livekit-server.exe`) и новый control API.
3. Задать `TS3STREAM_BUFFER_MODE=server`, `TS3STREAM_PLAYOUT_DELAY_MS=2000`. Не включать глобальный `room.playout_delay` в YAML.
4. Перезапустить **LiveKit и control API**: текущие стримы будут прерваны. TeamSpeak перезапускать не нужно. Старые комнаты должны быть закрыты; режим активных комнат не мигрируется.
5. Проверить версию `1.13.11-ts3stream.3`, capability endpoint, health control API и параметры новой комнаты.

Плагин 0.3.8 уже не применяет свою задержку к новому маркеру. Рекомендуется **0.3.9**: есть явная индикация серверного буфера, аудиодиагностика и ограничение очереди перед аудиоустройством до 80 мс вместо дополнительных 2 секунд. Это короткая очередь вывода, не новый A/V-буфер. Старый клиентский режим сохранён только для совместимости со старыми комнатами.

## Исправление пакетного кеша — серверная ревизия 2

В `1.13.11-ts3stream.1` был увеличен максимум кеша, но начальная ёмкость оставалась штатной: 70 аудиопакетов и 300 видеопакетов (видео могло адаптивно вырасти, например, до 1200). Это меньше двухсекундного потока при непрерывном звуке или высоком видеобитрейте. Пакеты терялись ещё во время серверного ожидания; появлялись `too much ext packets`, пропадание звука и остановки картинки. Синтетические сцены с редкими звуковыми импульсами не выявили проблему.

Ревизия `1.13.11-ts3stream.2` сразу выделяет серверным дорожкам 16 384 видеопакета / 2048 аудиопакетов. Обычные комнаты сохраняют прежнюю начальную ёмкость. Регрессии проверяют сохранность 500 аудио- и 5000 видеопакетов вместе с RTP-данными для повторной передачи, а также ограничение очереди при переполнении.

Для этого исправления нужен только новый бинарник LiveKit из [проверенного патча](../server/livekit/README.md) и перезапуск LiveKit. Плагин **0.3.9**, control API и настройки протокола не меняются. Номер плагина сам по себе не подтверждает наличие серверного исправления; проверяйте `livekit-server --version`.

## Восстановление порядка пакетов — серверная ревизия 3

Ревизия 2 устранила переполнение, но очередь сохраняла порядок прихода пакетов. Опоздавшие пакеты кадра попадали за пакеты следующих кадров. В реальном замере все части одного кадра уже находились на сервере за 1,75 с до отправки, однако передача кадра обоим зрителям растягивалась на 229 мс: сервер воспроизводил входящий джиттер вместо его устранения.

Ревизия `1.13.11-ts3stream.3` упорядочивает серверную очередь по расширенному номеру RTP-пакета и повторно проверяет её после ожидания срока отправки. Тесты проверяют переход через 65535, позднее восстановление во время ожидания, сохранность данных повторно помещённого в очередь пакета и воспроизведение обезличенной последовательности из 651 реального RTP-заголовка. Клиентская задержка не добавляется; плагин остаётся 0.3.9.

## Диагностика и ограничения

- `LiveKit server A/V buffer=2000 ms; client PCM compensation=0 ms` — серверный режим.
- `rtc audio_rx ... jitter_buffer_ms=... target_ms=... inserted=...` — внутренний аудиобуфер WebRTC.
- `audio playout queue_ms=... oldest_ms=... dropped_ms=...` — очередь вывода на аудиоустройство, отдельно от серверного буфера.

На сервере сохранены временные связи RTP/RTCP, общий NTP-мэппинг для дорожек одного автора и ограниченный пакетный кеш. При закрытии стрима буферизированный хвост отбрасывается. Длительный сбой источника, перегрузка декодера и плохой канал **сервер → зритель** не устраняются наличием серверного буфера.
