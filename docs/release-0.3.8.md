# TS3Stream 0.3.8 — буфер A/V и диагностика смен сцен

Пакет собран и проверен локально; действующий сервер не перенастраивался и не перезапускался.

## Изменения

- Потолок видеокодировщика по умолчанию снижен с 12 до **10 Мбит/с**. Сохраняется отладочное переопределение `TS3STREAM_MAX_BITRATE`. Это не жёсткий сетевой лимит: краткие пики, звук, RTP-заголовки и повторные передачи учитываются отдельно.
- Вместо автоматической подписки на всю комнату зритель запрашивает только публикации выбранного автора — как уже существующие, так и появившиеся после подключения. Без выбранного автора сохраняется прежняя подписка на все треки.
- Связанные аудио/видео публикуются с общим именем stream. Это само по себе не решает синхронизацию сырых аудиоколбэков с задержанным видео.
- Добавлен согласованный режим **2000 мс**: буфер видео WebRTC и ограниченная очередь PCM с такой же добавленной задержкой. Новый control API задаёт параметры при создании комнаты; клиент определяет режим по фактическим метаданным комнаты. Старые комнаты/серверы остаются без добавленной задержки. Очередь очищается при разрыве и закрытии; mute и громкость применяются при выводе.
- Новые установки Linux/Windows включают 2000 мс автоматически; зрителям нужен плагин 0.3.8+. Основные установщики сохраняют старую настройку при повторной установке. [Как включать и обновлять](buffered-playback.md).
- В `diag.log` добавлены `rtc tx` и `rtc rx` примерно каждые 2 секунды. Фоновый сбор не задерживает поток захвата, не накапливает незавершённые запросы и останавливается перед уничтожением комнаты.
- Счётчики: фактический битрейт/FPS за интервал, среднее время кодирования/декодирования кадра (`work_ms`), среднее ожидание пакета в очереди отправки или кадра в jitter buffer, потери, retransmit, отброшенные кадры, freezes, keyframes, NACK/PLI, целевой битрейт и реализация кодека. Поля, неприменимые к направлению, равны нулю; это не доказательство отсутствия проблем на противоположной стороне. `limitation` — числовое значение enum SDK. Первое наблюдение задаёт базу; короткий сеанс может не успеть вывести интервальную статистику.

Это подсчёт размеров SRTP-пакетов на интерфейсе сервера без сохранения медиасодержимого, не телеметрия кодировщика. FPS по RTP-маркерам около 27,3, а не гарантированное число декодированных кадров. В данном окне не обнаружены пропуски sequence number основного входящего видеопотока; это не исключает потери на других участках и в другое время. Обнаруженная неравномерность уже присутствует на входе SFU; разделить кодировщик, pacer и путь стример → сервер без клиентской статистики нельзя. Точную связь пауз с моментами смен сцен этот замер не устанавливает.

## Проверка дополнительного буфера

На отдельном локальном LiveKit с синтетическими 1080p сценами сначала проверены обычные настройки и задержка видео min=max=2000 мс с `sync_streams: true`, **ещё без компенсации PCM**:

| Режим | Медиана видео до колбэка | P95 видео | Медиана аудио до колбэка |
|---|---:|---:|---:|
| Без дополнительной задержки | 128,5 мс | 183,1 мс | 25,0 мс |
| Запрошено 2000 мс | 2026,6 мс | 2048,8 мс | 57,0 мс |

Это выявило необходимость отдельной задержки PCM. После её реализации и передачи согласованных настроек через токен комнаты:

| Сценарий | Медиана видео | Медиана аудио | Разница |
|---|---:|---:|---:|
| Обычное подключение | 2027,7 мс | 2046,9 мс | 19,2 мс |
| Поздний зритель | 2029,7 мс | 2047,8 мс | 18,1 мс |
| Повторное подключение viewer | 2032,1 мс | 2032,7 мс | 0,6 мс |
| Полный путь через собранный control API | 2025,7 мс | 2056,7 мс | 31,0 мс |
| Старая комната без буфера, новый токен запрашивает 2000 мс | 129,7 мс | 31,9 мс | прежний режим |

Проверки используют визуальные идентификаторы кадров и разные частоты звуковых импульсов. В буферизированном режиме тест требует задержку обеих дорожек около 2000 мс и разницу медиан менее 150 мс. Это выходные колбэки до панели/аудиоустройства. При первоначальном заполнении возможен разрыв между уникальными кадрами около 1,4 секунды и сброс ранних кадров; переподключение также требует нового заполнения. Буфер не восстанавливает потерянное содержимое источника и не гарантирует отсутствие всех пауз на плохом канале.

Действующий сервер по согласованному порядку обновления **пока не менялся**: сначала распространяются новые плагины, затем отдельно обновляется control API и включается режим для новых комнат.

Синтетический тест не насыщает потолок 10 Мбит/с и не доказывает, что снижение с 12 устранит паузы. Это умеренное снижение потребности в полосе ценой возможного ухудшения качества сложных сцен. Следующий предметный замер — `diag.log` автора и зрителя после установки сборки во время одинакового видео со сменами сцен.

## Проверка сборки

MSVC x64; `delayed_audio_test`, `rtc_diagnostics_test`, `video_send_queue_test`, `desktop_frame_test`, `source_picker_test`, `viewer_controls_test`, `viewer_autohide_test`, `live_stream_menu_test`; локальный `scene_change_test` с двумя авторами; `stream_ended_test` в режимах `static` и `resize` с восемью размерами до 2560×1440, в том числе с буфером. `go test ./...` и `go vet ./...`; тесты настройки установщиков Linux/Windows и синтаксис Bash/PowerShell. Результаты loopback не заменяют проверку в действующем TS3 и на ограниченном канале. Изменения 0.3.7 (DXGI и громкость 125%) входят в пакет; автоматический выбор DXGI ещё требует проверки на реальной Windows 10.

Установка: закрыть TS3, установить `dist/ts3stream-0.3.8.ts3_plugin`, запустить клиент заново. Для потолка 10 Мбит/с прежде всего обновить автора; для выборочной подписки и receive-диагностики — зрителей. Активный клиент автоматически не обновлялся.
