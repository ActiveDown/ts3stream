# TS3Stream 0.3.9 — серверный буфер A/V

## Исправление

Заменён рекомендуемый двухсекундный режим 0.3.8. В нём WebRTC постепенно увеличивал свою аудиозадержку, а плагин добавлял ещё фиксированные 2000 мс. Длинный тест воспроизвёл растущую рассинхронизацию, которой не было видно в коротких проверках.

Теперь **доработанный LiveKit удерживает и выпускает RTP аудио/видео по общей временной шкале автора**. Плагин в этом режиме не добавляет задержку PCM и не получает команду держать видео 2 секунды. Небольшие сетевые/аппаратные буферы остаются.

- Форк `1.13.11-ts3stream.1`, точный upstream commit, patch, Apache-2.0 license и проверенный build script находятся в [`server/livekit`](../server/livekit).
- RTCP sender reports связывают RTP-часы аудио и видео; абсолютные дедлайны не накапливают относительные ожидания. Пакетный кеш и очередь метаданных ограничены. При остановке старый хвост отбрасывается; просроченные пакеты не воспроизводятся пачкой.
- Control API проверяет capability endpoint сервера. Стандартный LiveKit не принимается как поддерживающий серверный буфер.
- Новые Linux/Windows-установки скачивают серверный форк и включают `TS3STREAM_BUFFER_MODE=server`, `TS3STREAM_PLAYOUT_DELAY_MS=2000`. Повторные установки сохраняют старые настройки, если режим явно не переопределён.
- Очередь **перед звуковым устройством** ограничена 80 мс вместо дополнительных 2 секунд; просроченный PCM удаляется, порядок waveOut-буферов при обходе кольца исправлен. Это короткая очередь вывода, не клиентская реализация двухсекундной задержки.
- Добавлены статистика аудиобуфера WebRTC, очереди аудиоустройства и индикация серверного режима.

## Измерения

Синтетические 1080p сцены и идентифицируемые звуковые импульсы; измерены выходные колбэки, **не физические экран/колонки**.

| Сценарий | Видео, медиана | Аудио, медиана | Аудио − видео |
|---|---:|---:|---:|
| Старый режим, после 120 с | 2027,5 мс | 2396,8 мс | +369,3 мс, тест FAIL |
| Серверный прототип, после 180 с | 2072,1 мс | 2073,1 мс | +0,9 мс |
| Финальная сборка + новый control API, после 180 с | 2070,0 мс | 2079,0 мс | +9,0 мс |
| Позднее подключение | 2083,7 мс | 2056,5 мс | −27,2 мс |
| Переподключение | 2059,6 мс | 2063,0 мс | +3,5 мс |

В финальном длинном локальном прогоне максимальный разрыв уникальных кадров после прогрева — 106,6 мс. Переподключение всё ещё требует получения ключевого кадра (измеренная пауза около 2,1 с). Старая комната без буфера сохранила прежний режим.

## Проверки

- MSVC x64 build; десять клиентских регрессий, включая новый bounded-audio тест и реальный silent waveOut smoke test (243840 отправленных сэмпл-фреймов, остановка 2,9 мс, без ошибок устройства).
- Пять моделируемых минут дрейфа/остановок вывода: старая FIFO доходит до 2000 мс, новая очередь не превышает 80 мс, максимальный возраст воспроизведённого PCM — 79 мс.
- Новый серверный scheduler: 30 моделируемых минут, разные RTP rates/offsets, rollover, NTP offset, переменная входящая задержка, отсутствие SR, скачок часов, отмена ожидания и старое поколение потока.
- Полные пакеты LiveKit `pkg/sfu` (`-test.short`) и `pkg/sfu/buffer` прошли в Linux/WSL. В Windows у upstream FEC-теста обнаружен нестабильный nil stats; он воспроизводится и с неизменённым upstream-файлом. Linux-прогон прошёл без исключения этого теста.
- Control API: `go test ./...`, `go vet ./...`, проверка отсутствия client playout delay в новых токенах и отказ на несовместимом SFU.
- Linux/Windows installer defaults, сохранение/переопределение режима и задержки; Bash/PowerShell syntax.
- Интеграция через реальные токены control API: длинный прогон, late join, reconnect, старая комната, static, восемь resize-стадий до 2560×1440 и закрытие viewer.
- Windows/Linux SFU повторно собраны из чистого checkout и опубликованного patch: бинарники побайтно совпали.

## Обновление

Нужно заменить **LiveKit и control API**, включить server mode и перезапустить оба сервиса. Текущие стримы будут прерваны; TeamSpeak перезапускать не нужно. [Порядок обновления, откат и ограничения](server-buffered-playback.md).

Рекомендуется плагин 0.3.9. Плагин 0.3.8 уже не включает свою PCM-компенсацию для нового серверного маркера, но не имеет новых диагностики/индикации/защиты очереди вывода.

Серверный буфер не устраняет потери/перегрузку на пути **сервер → зритель**, задержку устройства, перегрузку декодера или зависание источника. Проверки не гарантируют плавность на произвольном WAN. Автовыбор DXGI на физической Windows 10 остаётся отдельной проверкой из предыдущего релиза.
